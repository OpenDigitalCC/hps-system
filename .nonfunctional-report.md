## 1. Correctness and groundedness

**Method.** `perl -Ilib/perl -c` on `lib/perl/HPS/*.pm`, `bin/hps-onboard`, `t/*.t` (all clean); `shellcheck -s bash -S warning` on every added and modified shell file (below); structured review of the new trust-relevant paths (API caller identity, approver, audit intake, pairing, boot-NIC selection) against the failure-mode catalogue; cross-check of what the images contain against what the scripts call; cross-check of plan, ADRs and code.

**Findings with evidence.**

- Mechanical: `shellcheck -S warning` over all 18 files *added* since `91c9272` reports **0** findings. Over the 29 *modified* shell files the counts are unchanged or lower (e.g. `network-functions.sh` 35 -> 34, `supervisor-functions.sh` 2 -> 0; no file went up). `perl -c`: clean on all Perl files. No `hallucinated-package`: every Perl module is core (`JSON::PP`, `Fcntl`, `File::Temp`, `Test::More`, ...); the Nix inputs are `nixpkgs` and ctrl-exec.
- **plausible-but-wrong / unstated-assumption (needs a decision, not shim-detectable):** `http/api/api.sh:148` derives `CLIENT_IP` from `HTTP_X_REAL_IP`, then `HTTP_X_FORWARDED_FOR`, then `REMOTE_ADDR`. The line pre-dates the phase (`d0eb964`) but the phase now relies on it twice: line 151 grants localhost privileges when `CLIENT_IP == 127.0.0.1`, and line 545 passes `CLIENT_IP` to `ce_approve_pair_request` as the "API caller address" that CS-1.12 (`3964440`) binds a pairing request to. nginx here does not overwrite or strip `X-Real-IP` (`create-config-nginx.sh` only includes `fastcgi_params`), so a client on the provisioning LAN can send the header itself. This is **inferred from the code and not exercised** on hardware or in tests. If confirmed it weakens the ADR 0002 source-address binding and the "known host or localhost" authentication to a spoofable header. Highest-priority item in this report.
- **spec-drift (small, recorded):** `plans/phase-1.md` §2 says pairing is approved against `NETWORK_BOOT|INSTALLING`; the approver now also accepts `HELD` (audit image pairs). ADR 0002 was amended (26 lines changed) so this is documented, not drift.
- **architectural-drift:** none found against ADR 0001 (ctrl-exec runs node operations; OpenSVC is not on the NixOS images). ADR 0003 states Alpine scripts run unsandboxed; the NixOS executor with the `node` profile is a deliberate divergence recorded in its 2026-11-09 amendment. Not yet recorded in any ADR: the choice of **root plus a capability list** as the node-script containment (documented in `docs/SECURITY.md` "Node scripts under the executor", but a decision of ADR weight), and the **fixed image-wide ZFS host id** (`nix/modules/hps-common.nix:48`, comment only).
- **divergent-implementation:** (a) the registry exists twice — `lib/hps-registry.sh` (Bash) and `lib/perl/HPS/Registry.pm`; this is by design, and `test_p1_30_interop.bats` proves each reads the other's writes (shim-free). (b) `host_audit_refuse` is called through `cgi_fail`, which tests `FUNCNAME[1]` to avoid a double response (`lib/functions.d/cgi-functions.sh:79`) — a workaround, not a shared error path; listed in the known deferrals. (c) The audit image uses `<host>.<domain>` for the hostname and the node image the bare host name (`CS-1.15`); hps-run matches either. (d) `node-manager/base/n_api_client.sh:478` still uses `((failed++))`, which returns 1 under `set -e` when `failed` is 0; the brief forbids that form and the file is legacy, so it is reported, not fixed. (e) HPS still carries workarounds for ctrl-exec 0.14.1 quirks although 0.14.3/0.14.4 fix them (harmless duplication; each is a branch that is only exercised on old versions).
- **invalid-test risk:** the node image and audit image are built by `nix` which does not exist on this host; `test_p1_40_build_sh.bats` tests `build.sh` against a `nix` shim. `nix flake check` was run in the builder (phase-1.md §7) and the node image booted once on hardware, but the evaluation of `flake.nix` itself is not reproducible from the repository, see §6 (no `flake.lock`). The `scripts/tests/test_*.sh` legacy scripts "carry their own stubs" (known deferral) and are not run by the gate.
- **Hardware-verified facts:** UEFI PXE boot of audit and node images; time sync from the IPS chrony; unattended audit -> pair -> approve -> `ced ping` in about 2 s; `storage-pool-inspect` through the executor under the `node` profile matching the console result; ~32 s from boot script to operable over ctrl-exec for the node image (one boot). **Not hardware-verified:** two nodes at once (shared pairing window), re-provisioning of an already-paired node end to end with `--replace` on real nodes, Alpine/Rocky paths after the shared-code edits (only shim-tested), the BIOS (non-UEFI) branch of the dnsmasq `client-arch` split, IPS image rebuild from the Dockerfile with chrony (the image was built; `lighttpd` replacement CS-1.13 is queued and not built).

**Recommendations (ranked).**

1. Verify the `X-Real-IP` finding with a request carrying the header from a second address; if confirmed, take the caller address from `REMOTE_ADDR` only (the CGI server sits directly on the provisioning network) and add a bats test that a spoofed header changes nothing. Not fixed here (brief: fix nothing functional).
2. Record two ADRs or ADR amendments: node-script containment (root + capability list under the executor) and the image-wide ZFS host id with its phase-2 retirement.
3. Retire the 0.14.1 workarounds once no 0.14.1 agent can exist (images pin ctrl-exec 0.14.4).
4. Replace the `FUNCNAME` check in `cgi_fail` with a shared refusal path.

## 4. Performance

**Method.** No performance baseline is declared in the repository or the brief beyond the owner's remark that boot should be quick. Measured what could be measured here; took the hardware numbers from the inventory file; proposed a baseline.

**Findings with evidence.**

- Boot to operable (hardware, **one** node-image boot, 2026-11-09 16:44 UTC): boot script issued 16:44:01, kernel and 573 MB initrd served by 16:44:04, bundle fetched 16:44:22, paired 16:44:33 as `sch-001`; first `hps-run` answered at uptime 0:00. About **32 s from boot script to operable**, about 1 min from iLO reset including POST. RAM in use after boot 3.66 GiB of 256 GiB (store 573 MB squashfs). Audit image idle: 4.5 GiB RAM in use, store 1.4 GiB squashfs. These are single observations, not distributions.
- Image size: roughly 2.5 GiB of artefacts per pin on the IPS and ~3 GiB of closures per build in the builder store (phase-1.md §7); the disk filled once (vdc1 at 100%) and 30 GiB was recovered by hand. There is no `nixos-prune-pins` and no GC in the builder (known deferral).
- Controller code: Perl registry, 2,000 `system_set` calls in a temp config base took **0.62 s** (0.31 ms per write including lock file, temp file and rename); 2,000 `system_get` calls took **0.07 s** (0.035 ms). The Bash registry was not benchmarked. Registry I/O is one file per key; `list` is a directory read. No O(n^2) shape found in the new code; `host_list_all` scans the hosts directory once.
- Test suite: the full gate (bats + prove + shellcheck) takes **more than three minutes** on this host (it was moved to the background by the 180 s timeout). The per-commit gate cost is now long enough to affect how often it is run.
- Not measured: IPS request latency under concurrent nodes, TFTP throughput for `snponly.efi`, dnsmasq reload time, the 573 MB initrd transfer rate with more than one node, `nix build` wall time, rsyslog throughput at 514/tcp. No profiler was run (`NYTProf` absent).

**Recommendations.**

1. Propose and record a baseline: node boot script to operable <= 60 s for one node on a 1 GbE segment, RAM overhead of the image <= 5 GiB, audit round trip <= 10 s; re-measure with five nodes booting together in phase 3 (this is the first real load test, and it also exercises the shared pairing window).
2. Add `nixos-prune-pins` and a post-publish GC in phase 2 (it is a disk-full outage, not a speed problem, and has already happened once).
3. Split the gate into a fast tier (changed-file bats + prove) and a full tier to keep the supervisor loop short; do not optimise anything else without a measurement.

## 5. Reliability and resilience

**Method.** No SLOs, error budgets, RTO/RPO or capacity tests are declared for the lab IPS (`docs/POLICY.md`, `docs/SECURITY.md`, the plans). The IPS is a single-container, single-instance lab service under the open-source regime; waiving a *full* SLO set is reasonable, a *minimal* statement is not yet there. Failure behaviour was reviewed from the code and from the bring-up record.

**Findings with evidence.**

- **Declarations:** SLO, error budget, RTO, RPO — none recorded. Proposed minimal set below.
- **Stateless nodes by design:** a node's root is RAM; a lost node loses nothing HPS owns; the IPS registry (`hps-config`) and `hps-log` are the only state. There is **no backup or restore procedure** for the IPS working folder, and no check that a restored folder boots a node.
- **Failure handling that exists and is shim-tested:** the approver denies on any failed binding check and logs; `node_audit` refuses over-size bodies (413) and non-`HELD` hosts; `hps-time` and `hps-log-target` retry with bounded waits; ZFS is never force-imported (`b57168e`); pool inspection imports foreign pools read-only and exports again; `hps-pair` has a bounded background poll for the request id; the approver closes the pairing window after approval.
- **Failure handling found only on hardware (bring-up record):** first-boot clock in 2001 (time), the pairing request missing the 300 s window, the node taking a lease on the wrong LAN, the executor without capabilities, the dispatcher registering `host..` — all fixed during bring-up (CS-1.9, 1.12, 1.14, 1.15, 1.16). This is evidence that the shims did not model these failures; expect the same class in phase 2.
- **Single points and known weak spots:** one shared pairing window per IPS (two nodes booting together contend; deferred to phase 3/4); the image-wide ZFS host id (two nodes with the same id will refuse each other's pools — safe, but a surprise); the static-IP allocator ignores reserved addresses and handed out the host's own lab-shim address (`.2`); stale dispatcher registrations need ctrl-exec `remove-agent`; the IPS is a hard dependency for time, logging and pairing, and a node that boots while the IPS is down gets no clock, no log forwarding and no ctrl-exec.
- **Fault injection run:** none in the suite or on hardware, except what bring-up hit by accident. Never exercised: IPS restart during a node boot, dispatcher down during pairing, disk full on `hps-log` or `hps-resources`, certificate expiry (the agent certificate is re-issued every boot, so expiry is unlikely; the dispatcher CA lifetime is not recorded), power loss to the IPS host. No capacity test.

**Recommendations (missing declarations first).**

1. Record a minimal SLO block in `docs/OPERATOR.md` (to be created): IPS boot-service availability (best effort, lab), RTO for the IPS = rebuild container and restore `hps-config`, RPO = last copy of `hps-config` (propose daily). An undeclared target cannot be met or breached.
2. Write and test a backup/restore for `hps-config`, `hps-resources/packages` and the dispatcher CA directory (`/etc/ctrl-exec-dispatcher`, which is the one irreplaceable secret on the IPS).
3. Fault injection in phase 3, ranked by likelihood x blast radius: IPS container restart mid-boot; two nodes pairing together; dispatcher unreachable; `hps-log` disk full.
4. Fix the allocator (declared static range plus reserved list) before a second static node is added.
5. Make the pairing window per node (a map keyed by MAC) before phase 3.

## 6. Security

**Method.** `gitleaks detect` over the full history; `perlcritic --theme security`; manual audit of untrusted-input entry points (CGI, API, audit POST, pairing report), of `eval`/`system`/command construction in new code, and of the trust boundaries in `docs/SECURITY.md`; SBOM regeneration and drift check; review of the Nix modules for what the images expose. No `trufflehog`, `debsecan` or pentest tooling was run.

**Findings, grouped.**

- **Secrets:** `gitleaks detect` — 443 commits scanned, **no leaks found**. `test_p1_43_no_secrets.bats` asserts the image sources carry no secret. The iLO credential is in `lab/secrets/` outside the repository. The DL360 inventory file and the new docs carry no credential or real host name; the test fixtures for the cluster bootstrap and chrony (`test_p1_80`, `test_p1_90`) use the lab provisioning subnet `10.100.1.0/24`, which is a private range but not a `$VAR` placeholder as the brief's convention requires. Low severity; listed in §8.
- **Input handling:** `node_audit` has a size cap and state check (`host-functions.sh:873-903`) and stores the body after a `jq` schema check (`host-functions.sh:886`); pairing reports are checked in `ce_approve_pair_request` (MAC state, hostname, source address, window). **High, inferred, unexercised:** client-controlled `X-Real-IP`/`X-Forwarded-For` determine `CLIENT_IP` (`api.sh:148`), used for the loopback authentication branch (`api.sh:151`) and for the approver's caller-address binding (`api.sh:545`); see §1. The approver's other bindings (MAC registry state, hostname first label, source IP from the dispatcher's own list, time window, one approval per cycle) are independent of the header, so the damage is bounded to weakening one of four checks and to the loopback branch (which the API gates by action).
- **Auth and authz:** boot identity is MAC on an isolated VLAN (accepted, documented in "Node identity at boot"). Post-enrolment identity is ctrl-exec mTLS. Enrolment is auto-approved by the registry-bound approver (ADR 0002); the window is a single, IPS-wide, 300 s window opened by each NixOS boot script. A HELD node that pairs becomes manageable over ctrl-exec before any human decision (by design: it is how the audit and pool inspection work); the node scripts reachable by an audit-image agent are the same read-mostly set, but the profile is `node` (root + capabilities) for every script and image. `hps-onboard assign` is a local human action; no remote path assigns.
- **Node privilege:** every allowlisted script runs as root with a fixed capability list and `no_new_privileges`, no `writable` list (`docs/SECURITY.md`, "Node scripts under the executor"). Containment rests on the allowlist and per-script argument checks, which are written to be the manual runbook. `services.openssh.enable = false` in `hps-common.nix`; `openFirewall = true` for the agent port (7443); the console autologins as root on the audit image (documented lab aid, `hps-audit.nix:30`) and the serial getty on ttyS0/ttyS1 is enabled on all images. The audit image is network-reachable as root through ctrl-exec before any approval of the machine's role.
- **Crypto:** nothing custom. mTLS and the CA belong to ctrl-exec 0.14.4. The keysafe "secure" mode is still a stub (`keysafe-functions.sh:129`, legacy, phase 2 deliverable); there is no secret in any image, which the phase relies on.
- **Filesystem:** `nix/build.sh` and the CGI intake use temp-then-rename in the target directory; the Perl registry uses `.lock/<KEY>.lock` with temp-then-rename. Test scripts create temp dirs with `mktemp -d`. Nothing world-writable found in the added code. The build volume rule (no `/nix` bind mount under `/srv/projects`) is documented in the builder README.
- **Supply chain / dependencies:** (a) **`flake.lock` is not committed** (`flake.nix` header comment): the nixpkgs revision and the ctrl-exec revision are chosen at build time and recorded only in the served `boot.json`, so the repository does not reproduce an image; the ctrl-exec input is `github:OpenDigitalCC/ctrl-exec` unpinned, with the builder overriding it by a local export. The `system_pin` mechanism protects a *node* from drifting, not the *source* from drifting. (b) ctrl-exec is pinned to a release tarball (0.14.4) for the dispatcher. (c) Debian components in the IPS image resolve at build time (stated in the SBOM). No CVE scan was run (`debsecan` and a Nix vulnerability scanner are not installed on this host).
- **SBOM:** regenerated in this changeset by hand (the file has no generator in `scripts/`; the convention is a hand-maintained CycloneDX 1.6 file with `version: "trixie"` for Debian packages, and `rules/release-workflow.md` names no strict check for a bash/Nix project). Changes: version 1 -> 2; ctrl-exec 0.12.3 -> 0.14.4; added `chrony`, `perl-modules-5.40` (core modules), and the packages the IPS Dockerfile installs that the file was missing (`git`, `ipcalc`, `tcpdump`, `iputils-ping`, `ca-certificates`); added the NixOS 26.05 node component set (`nixos`, `systemd`, `rsyslog`, `zfs`, `bash`, `coreutils`, `curl`, `jq`, `iproute2`, `gawk`, `gnutar`, `findutils`, `gnugrep`, `procps`, `util-linux`, `pciutils`, `usbutils`, `smartmontools`, `numactl`) and the build-time `nix` builder image. 52 components now. Not listed on purpose because they are not in any image: libvirt/QEMU/OVMF (phase 3), mdadm, targetcli (phase 2). Stale entries: `tftpd-hpa` is installed but TFTP is served by dnsmasq (kept, noted in its description); `vim` is installed in the image and not listed (editor, not a dependency). A mechanical drift check (code `use`/`source` versus the SBOM) does not exist for Bash or Nix.
- **Threat model:** `docs/SECURITY.md` has a STRIDE pass, trust boundaries and (new) "Node identity at boot" and "Node scripts under the executor" sections. It does not yet list: the shared pairing window, the audit image's pre-approval manageability, the `X-Real-IP` issue, the missing `flake.lock`, and the loss of the dispatcher CA as a risk. No pentest report exists; the lab segment is isolated and the regime (open-source steward) does not require one.

**Recommendations (exploitability x impact).**

1. **Fix this release (phase 2 start):** `CLIENT_IP` from `REMOTE_ADDR` only, with a test (see §1).
2. **Fix this release:** commit `flake.lock` generated in the builder and pin the ctrl-exec input to a tag or revision; add a bats check that `flake.lock` exists.
3. Per-node pairing windows and a pairing token (the keysafe second factor already named in ADR 0002) once the secure mode exists.
4. Decide whether the audit image should be limited to the read-only scripts (a separate allowlist for the audit image); today the audit image and node image share the same script set.
5. Add the five missing items to `docs/SECURITY.md` "Open hardening items".
6. Install `debsecan` (IPS image) and a Nix scanner (`vulnix`) in the builder and run them at the next close-out; hardening, can wait.
7. Replace the hand-maintained SBOM by a small script (the lazysite `manifest-to-sbom.pl --strict` pattern) when a second project needs the same.

## 7. Documentation
