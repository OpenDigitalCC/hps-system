# ADR 0005 — The IPS drives a node's storage role over ctrl-exec

- Status: accepted
- Date: 2026-11-09
- Tags: storage, secrets, ctrl-exec, zfs, iscsi

## Context

Phase 2 puts a ZFS mirror pool, an encrypted parent `<pool>/enc` and iSCSI
exports on a storage node (type SCH). The node scripts
(`node-manager/nixos-26/scripts/`) are single actions behind the ctrl-exec
allowlist. Something on the IPS has to decide when each runs, supply the key
that unlocks `<pool>/enc`, and refuse destructive actions without a human.

## Decision

`HPS::Storage` (`lib/perl/HPS/Storage.pm`) and `bin/hps-storage` are that
driver. They call node scripts only, never a shell on the node.

Operations (all take `--dry-run`, which prints the node calls and redacted
input documents and changes nothing; all are idempotent):

- `up`: `storage-pool-import <pool>`, `dataset-unlock <pool>/enc`,
  `iscsi-export` for each entry of the host's registry key `storage_exports`
  (`[{zvol, iqn, initiator, portal}]`); then `storage_state=up`. `up` uses the
  existing key only: no key in the keysafe means "pool not created by HPS"
  (exit 4) and nothing is sent.
- `down`: `iscsi-unexport` for each export; `storage_state=down`. It never
  exports or unloads the pool; a node reboot does that.
- `create <pool>`: needs an unexpired `pool-create` approval for this host and
  pool. One `storage-pool-create` call carries the approval, the cluster
  approval secret and the `enc` key (generated by the keysafe if absent), then
  `up`.
- `destroy <pool>`: needs a `pool-destroy` approval. One `storage-pool-destroy`
  call; the `storage_*` registry keys are cleared. The key is not deleted.
- `trim-check`, `status` (read-only `storage-status`; see the amendment below).
- `forget-key`: the only way a key leaves the keysafe. Refused while the
  registry still records a pool unless `--yes`.

The pool is named after the active cluster (owner ruling 2026-11-09);
`create` and `destroy` refuse any other name unless `--allow-any-pool-name`.
`create` and `destroy` print the approved by-id disks before sending anything.

### Keys

The `enc` key is 32 random bytes in the IPS keysafe (`HPS::Keysafe`), never in
the registry, an image, a plan, a log line or an argument. On the node it exists
only in RAM: `dataset-unlock` pipes it to `zfs load-key -L prompt`; nothing is
written to disk, so a rebooted node cannot unlock its pool until the IPS
delivers the key again. Plans show `"<redacted: ...>"` for the key, the secret
and the approval signature.

### Approvals

Approvals are created by a human (`hps-approve`), signed with the cluster
approval secret, bound to host, pool, disks and expiry (1 h). `hps-storage`
verifies signature, expiry, host, pool and action before it sends anything;
the node verifies the same HMAC again with the secret delivered in the same
document.

### Delivery: the exact ctrl-exec mechanism

The destructive scripts and `dataset-unlock` are `input = raw` in `scripts.conf`:
the agent puts the bytes of ONE input field on the script's stdin. On
ctrl-exec 0.14.4 `ced run <agent> <script> [-- args]` has no input option; run
input exists on the API (`POST /run`, member `input`) and its client
`ctrl-exec-cli run <agent> --script <s> --input - [--json] -- args`, which
sends all of its stdin as the single field `input`. `scripts/hps-run.sh
--input [--json] <host> <script> [args]` does the name resolution as before
and calls exactly that; without `--input` it still calls `ced run` (via
`ce_run`, unchanged). `HPS::Storage::Runner::HpsRun` uses `--input --json`
when a call has a document and reads the node script's `exit`, `stdout` and
`stderr` from the JSON result. `CTRL_EXEC_CLI` names the client,
`CTRL_EXEC_API_SOCKET` (or `CTRL_EXEC_API_URL`) the API; input should travel
only over the API's unix socket or TLS.

Prerequisite: the IPS needs `ctrl-exec-api` running with an `api_socket` and
`ctrl-exec-cli` (from the ctrl-exec plugins) installed, and the user running
`hps-storage` allowed on that socket. Neither is part of the IPS image today.

### After pairing

`http/api/api.sh`, after `ce_approve_pair_request` succeeds, starts
`hps-storage <mac> up --wait 120` detached (`setsid`, stdin/stdout/stderr on
`/dev/null`) for a host whose TYPE contains SCH and whose registry has
`storage_state`. Otherwise it only logs. `--wait` retries the first call while
the agent is not yet registered. The job logs through `logger -t hps`.

## Consequences

- A node loses its key on every reboot; `up` after pairing restores it. If the
  IPS is down at that moment the pool stays imported-but-locked until
  `hps-storage <host> up` is run.
- Running identity: the keysafe is 0700 and refuses files not owned by the
  running uid, while the CGI runs as `www-data`. The hook's job therefore fails
  with a `perms` error unless `HPS_STORAGE_CMD` points at something that runs
  as the keysafe owner. Choosing that mechanism is open (see CS-2.3 report).

## What a human does by hand

```
hps-storage $NODE status
hps-approve pool-destroy $MAC --pool $OLDPOOL
hps-storage $NODE destroy $OLDPOOL --allow-any-pool-name
hps-approve pool-create $MAC --pool $POOL --disk $BYID1 --disk $BYID2
hps-storage $NODE create $POOL --dry-run
hps-storage $NODE create $POOL
hps-storage $NODE up
hps-storage $NODE trim-check
hps-storage $NODE down
hps-storage $NODE forget-key --yes
```

Without the driver, the same calls from the IPS (each `input = raw` document
on stdin from a 0600 file, never on a command line; `$DOCFILE` holds the JSON
the script header documents):

```
scripts/hps-run.sh $NODE storage-pool-import $POOL
scripts/hps-run.sh --input $NODE dataset-unlock $POOL/enc < $KEYDOCFILE
scripts/hps-run.sh $NODE iscsi-export $POOL/enc/$ZVOL --iqn $TARGET_IQN --initiator $INITIATOR_IQN --portal $PORTAL
scripts/hps-run.sh --input $NODE storage-pool-create $POOL --disk $BYID1 --disk $BYID2 --approval-file - < $DOCFILE
```

## Amendment 2026-11-09 (CS-2.5): zvols and exports belong to the storage role

A zvol is created, listed, exported, unexported and destroyed through the same
driver; none of it is a separate role. A zvol is `<pool>/enc/<name>`, one level
below the encrypted parent, so it is only ever created on an unlocked parent.

- `zvol-create <dataset> <size>` (`storage-zvol-create`): sparse, `volblocksize=16k`,
  `compression=lz4`; `keystatus` of `<pool>/enc` must be `available`. A zvol of the
  same size already there is a no-op; anything else is refused.
- `zvol-list` (`storage-zvol-list`) and `status` (`storage-status`: pool status,
  keystatus, zvols, exports) are read-only. `status` no longer imports the pool.
- `export <dataset> --iqn --initiator [--portal]` runs `iscsi-export` and records
  `{zvol, iqn, initiator, portal}` in `storage_exports` once the node succeeded
  (the portal defaults to the host's registry `IP`); `unexport <iqn>` runs
  `iscsi-unexport` and removes the entry. One zvol is exported under one iqn.
  `up` exports every recorded entry again after unlocking, which is how an
  export survives a node reboot.
- `zvol-destroy <dataset>` (`storage-zvol-destroy`, `input = raw`) is destructive
  and follows the pool-destroy path: a human runs `hps-approve zvol-destroy <mac>
  --dataset <dataset>`. The approval keeps the eight-member canonical form and the
  same HMAC; action is `zvol-destroy`, `pool` carries the dataset name, `disks`
  is empty and `wipe` is 0. The registry key maps `/` to `__`
  (`approval_zvol-destroy_lab__enc__t0`). An approval for the pool never approves
  a zvol and the other way round (the action and the `pool` member are both
  checked, on the IPS and again on the node). The IPS refuses a zvol still in
  `storage_exports`; the node refuses one a LIO backstore names or that is
  mounted or has holders; it fails closed if LIO cannot be listed.

`trim-check` records `storage_trim_verdict` from the script's stdout (the last
line starting `TRIM `, else the last non-empty stdout line), never a `+ cmd`
trace from stderr, and `storage_trim_ok` (0|1). A failing verdict (exit 3) is
recorded too.

The export is proved from the IPS with `scripts/hps-iscsi-test.sh <ip> <iqn>
[--initiator-name <iqn>]` (open-iscsi is in the IPS image for this): discover,
login, write and read back 4 MiB at 1 GiB - 8 MiB, logout. It is the only place
HPS writes to a LUN, and the LUN is a test zvol. The host kernel must have
`iscsi_tcp` loaded; a container cannot load it, and the script says so.
