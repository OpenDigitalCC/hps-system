# Resource monitoring

The IPS asks every paired node, on a fixed interval, how much of its resources
it is using, and writes the answers to syslog. It is for getting a sense of
use (the owner's request of 2026-11-11); it raises no alarms and keeps no history
beyond the log.

## What runs where

- On each node (node-base, node-converged; not the audit image): the ctrl-exec
  `nagios-check` agent script from the pinned `ctrl-exec-plugins` input
  (release tag in `flake.nix`), allowlisted as the node script `nagios-check`
  under profile `node`. It reads no input; its arguments are check names.
  `nix/modules/hps-monitor.nix` installs it, a directory of plugins
  (`check_disk`, `check_load`, `check_swap`, `check_procs` from
  monitoring-plugins, `check_mem` from the plugin repository, and HPS's own
  `check_zpool`, `check_fs` and usage checks `check_cpu`, `check_net`,
  `check_diskio`, `check_zpool_io` and `check_vms`) and
  `/etc/nagios-checks/checks.conf`.
- On the IPS: `bin/hps-monitor`, supervisor program `hps-monitor` running
  `hps-monitor loop`. It calls `scripts/hps-run.sh --json <fqdn> nagios-check --all`
  for each paired node and logs the result.

The targets are the paired nodes only: hosts of the registry that the dispatcher
also lists as agents (names starting `stale-` are ignored). No node script runs
on the IPS; a run of every node also checks the IPS's own resources and log
filesystems locally (see below). The host the IPS runs on is never checked.

## Who decides what

| Decided | By | Where |
| --- | --- | --- |
| Which checks run | the IPS, as `--all` (every check the node offers) | `bin/hps-monitor` |
| When | the IPS | cluster key `monitor_interval_seconds` |
| What a check name means: plugin, thresholds, timeout | the node | `/etc/nagios-checks/checks.conf`, generated by `hps-monitor.nix` |

The IPS sends the script name and `--all` and nothing else.

## The node's checks

| Name | Plugin and arguments | Where |
| --- | --- | --- |
| `disk_root` | `check_disk -w 20% -c 10% -p /` | every node |
| `load` | `check_load -r -w 1.5,1.2,1 -c 3,2.5,2` | every node |
| `mem` | `check_mem -w 10 -c 5` | every node |
| `procs` | `check_procs -k -w 1000 -c 2000` (user-space processes; kernel threads left out) | every node |
| `swap` | `check_swap -w 30% -c 10%` | only a node with swap configured |
| `zpool` | `check_zpool` (pool health; DEGRADED is WARNING, FAULTED and worse CRITICAL; capacity as perfdata) | storage nodes |
| `zpool_io` | `check_zpool_io` (pool I/O and capacity in bytes, see below) | storage nodes |
| `zpool_cap` | `check_zpool -m cap -w 80 -c 90` (how full each pool is, see below) | storage nodes |
| `disk_var_lib_containers`, `disk_var_lib_hps_ips` | `check_fs -p <mount> -w 80 -c 90` (the CNH state disk, see below) | container hosts |
| `disk_var_lib_hps_builder` | `check_fs -p /var/lib/hps-builder -w 80 -c 90` (the builder disk) | builders |
| `disk_other` | `check_fs -a -x <the role mounts> -w 80 -c 90` (every other persistent filesystem) | every node |
| `cpu` | `check_cpu` (CPU time by state, see below) | every node |
| `net` | `check_net` (traffic per interface, see below) | every node |
| `diskio` | `check_diskio` (throughput per whole disk, see below) | every node |
| `vms` | `check_vms` (CPU, memory, disk and network per running guest, see below) | compute nodes |

A netbooted node runs from RAM: `/` is a tmpfs and the store is a squashfs.
`disk_root` therefore measures RAM taken by files written to `/`, and `mem` the
RAM left. The persistent filesystems and pools are the `disk_*` checks and
`zpool_cap` (below). Other thresholds are the plugin's example values.

## Persistent filesystems and pools

A full persistent disk stops what lives on it (lab 2026-11-12: cnh-001's
state disk filled, "No space left on device", and no check covered it). These
checks grade space and inode use, WARNING at 80% used or more and CRITICAL at
90%, the higher of the two counting:

- `disk_<mount slug>` (`check_fs -p`): one per role disk the image mounts,
  the slug being the mount point with `/` and `-` as `_`. Not mounted (no
  disk prepared yet) or on tmpfs is OK and says so: the data is then on the
  RAM root, which `disk_root` watches.
- `disk_other` (`check_fs -a`): every other mounted filesystem except RAM and
  pseudo filesystems (tmpfs, overlay, squashfs, proc, sysfs, cgroup, ...),
  network filesystems, ZFS (its datasets share the pool: `zpool_cap`), the
  role mounts above and a second mount of the same device (a bind mount).
  No such filesystem is OK. A check per mount point is not possible for
  these: `checks.conf` is fixed in the image and they are only known at run
  time, so their figures carry the slug as a prefix (`srv_used_pct`).
- `zpool_cap` (`check_zpool -m cap`): capacity of each imported pool from
  `zpool list`, health aside (that is `zpool`).

| Check | Status line and perf labels |
| --- | --- |
| `disk_<slug>` | `DISK OK - /var/lib/containers 41% used (12.3 GiB of 30.0 GiB), inodes 3%`; `used_pct`, `inode_pct` (left out where the filesystem has no fixed inode count), `used`, `size` (B) |
| `disk_other` | `DISK OK - 2 filesystems: /srv 41% (inodes 3%); /data 12% (inodes 1%)`; the same labels prefixed `<slug>_` |
| `zpool_cap` | `ZPOOL_CAP OK - 2 pools: lab 41% fast 3%`; `<pool>_cap` |

The thresholds are cluster keys, `monitor_disk_warn_pct` (default 80) and
`monitor_disk_crit_pct` (default 90). The node grades at 80 and 90 (they are
in its image); hps-monitor grades the same figures (`used_pct`, `inode_pct`,
`<pool>_cap`) again with the keys, so a change takes effect at the next tick
with no new image. A state the IPS changed says so in the line: `(graded at
warn 70% crit 85%)`. A warn not below crit, or a value outside 1 to 100, is
logged once and both defaults are used. `hps-ips-check` grades its `disk
resources` and `disk log` checks with the same keys.

The IPS's own filesystems: a run of every node (the loop's, or `hps-monitor
run` with no `--host`) also measures the filesystems of `$HPS_RESOURCES` and
`$HPS_LOG` with `df` and logs them as host `ips.<cluster domain>`, checks
`disk_resources` and `disk_log`, in the same form as a node's:

```
hps-monitor: host=ips.lab.hps check=disk_log state=CRITICAL DISK CRITICAL - /srv/hps-log 97% used (95.0 GiB of 97.9 GiB), inodes 34% on /srv | used_pct=97% inode_pct=34% used=...B size=...B
hps-monitor: host=ips.lab.hps checks=2 worst=CRITICAL duration=0.0
```

The node checks take effect with a new node image; the IPS's with the IPS's
tree.

## Usage checks: trend and baseline data

`cpu`, `net`, `diskio`, `zpool_io` and `vms` exist to collect numbers, not to
raise alarms (owner, 2026-11-11: data for trends as the lab scales out, and a
baseline for when it is put under pressure). Each is OK whenever it can read its
source, and says UNKNOWN only when it cannot (a missing `/proc/stat`, `zpool` or
`virsh` failing). The one exception is optional: `check_cpu -w BUSY -c BUSY`
applies thresholds to the busy percentage; `checks.conf` sets none.

Each takes two samples of a counter one interval apart (`-i SECONDS`, 1 to 5,
default 1) and reports the difference as a rate, so a value is the average over
that one second, not over the tick; the log line is a snapshot. `check_zpool_io`
asks `zpool iostat -Hp 1 2` and uses its second sample.

Perf labels are lower-case `[a-z0-9_-]` (dots and other characters in interface,
pool and guest names become `_`; the pool, disk, interface or guest name comes
first). The suffix says what the number is:

| Suffix or unit | Meaning |
| --- | --- |
| `_Bps` | bytes per second (plain number) |
| `_pps` | packets per second |
| `_iops` | operations per second |
| `%` | percent of the interval (or of a vCPU, see `vms`) |
| `B` | bytes, a level (`_alloc`, `_free`, `_rss`, `_mem`) |
| `c` | a counter's increase over the interval (errors, drops) |

| Check | Status line and perf labels |
| --- | --- |
| `cpu` | `CPU OK - 3.2% busy (iowait 0.1%, steal 0.0%)`; `busy` (100 - idle - iowait), `user`, `nice`, `system`, `iowait`, `irq`, `softirq`, `steal`, `idle` as % of the interval; `cpus` |
| `net` | `NET OK - rx 1.2 Mbit/s tx 0.4 Mbit/s (3 interfaces)`; per interface `<if>_rx_Bps`, `_tx_Bps`, `_rx_pps`, `_tx_pps` and `_rx_errors`, `_tx_errors`, `_rx_dropped`, `_tx_dropped` (counter deltas, `c`). Left out: `lo`, `veth*`, `vnet*` (guest taps; see `vms`) and interfaces that are down |
| `diskio` | `DISKIO OK - read 1.2 MB/s write 3.4 MB/s (2 disks)`; `disks`, and per whole disk (`sd*`, `vd*`, `xvd*`, `nvme<N>n<M>`; no partitions, `dm-*`, `md*`, `zd*`, `loop*`, `ram*`) `<dev>_rd_Bps`, `_wr_Bps` (sectors x 512), `_rd_iops`, `_wr_iops`, `<dev>_busy` (% of the interval with I/O in flight). A RAM node has no disk: `DISKIO OK - no disks | disks=0` |
| `zpool_io` | `ZPOOL_IO OK - read 2.0 MB/s write 3.5 MB/s (2 pools)`; `pools`, per pool `<pool>_alloc`, `_free` (B), `_rd_iops`, `_wr_iops`, `_rd_Bps`, `_wr_Bps`. No pool: `ZPOOL_IO OK - no pools` |
| `vms` | `VMS OK - 2 running VMs (rss 1.5 GiB)`; `vms`, per running guest `<vm>_cpu_pct` (guest CPU time / interval; 100% is one full vCPU, so it can exceed 100), `_vcpus`, `_rss` (host memory the guest process holds), `_mem` (memory given to the guest), `_rd_Bps`, `_wr_Bps` (summed over its disks), `_rx_Bps`, `_tx_Bps` (summed over its NICs). No guest: `VMS OK - no running VMs | vms=0` |

Time budget: `nagios-check` runs the checks one after another within its 50 s
budget, 10 s at most each. The five samplers add about 5 s to a node's run (the
`cpu`, `net`, `diskio`, `zpool_io` and `vms` waits do not overlap), well inside
the budget at the lab's 30 s interval, but a shorter `monitor_interval_seconds`
or more samplers would not be. Each plugin finds its tools itself: the build
puts coreutils and awk on its `PATH` and, for `zpool_io` and `vms`, the
absolute store path of `zpool` and `virsh` (libvirt is on compute nodes with the
compute profile).

## Log lines

Every line goes to syslog (tag `hps`, facility `local0`; OK is `info`, WARNING
`warning`, CRITICAL, UNKNOWN and UNREACHABLE `err`) and, for `hps-monitor run`,
to stdout. OK results are logged too.

```
hps-monitor: host=sch-001.hps.test check=mem state=OK MEM OK - 62% available (9.8 GiB of 15.6 GiB) | available=10522MB available_pct=62%
hps-monitor: host=sch-001.hps.test checks=6 worst=OK duration=1.4
hps-monitor: host=tch-002.hps.test state=UNREACHABLE hps-run exit 4: hps-run: no registered agent for tch-002.hps.test
hps-monitor: tick hosts=3 duration=1.9
```

- `host=<fqdn> check=<name> state=<state> <summary> | <label=value[unit] ...>`:
  one per check; the performance data is omitted when the plugin gave none.
- `host=<fqdn> checks=<n> worst=<state> duration=<s>`: one per host.
- `host=<fqdn> state=UNREACHABLE <reason>`: the node could not be asked (not
  registered, call failed or timed out after 70 s, unreadable reply).
- `host=<fqdn> state=PAIR_FAILED since=<UTC time> reboots=<n> ...` (`err`):
  the IPS gave up pairing the host (registry `pair_failed_at`, ADR 0002
  amendment 2026-11-12). It is not paired, so it is not checked; the loop logs
  the line when it first sees it and then every 10 minutes.
- `tick hosts=<n> duration=<s>`: one per run, so the cadence is visible.
- `tick skipped missed=<k> run=<s>s interval=<n>s`: a run took longer than the
  interval; the ticks it covered are skipped (runs never overlap).
- `disabled (monitor_interval_seconds=0)` and `enabled interval=<n>s`.

Nodes are called in parallel, eight at a time.

## The interval

Cluster key `monitor_interval_seconds`: `0` disables, otherwise 10 to 86400
seconds; default 60 (a value outside the range is logged and 60 used). It is read
before every tick, so a change applies at the next one; while disabled the loop
rechecks the key every 60 seconds. `hps-cluster-config set monitor_interval_seconds 30`.

## Commands

```
hps-monitor run [--host <host>]... [--parallel N]
hps-monitor loop [--max-ticks N]
hps-monitor interval
```
