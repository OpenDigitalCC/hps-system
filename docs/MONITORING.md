# Resource monitoring

The IPS asks every paired node, on a fixed interval, how much of its resources
it is using, and writes the answers to syslog. It is for getting a sense of
use (the owner's request of 2026-11-11); it raises no alarms and keeps no history
beyond the log.

## What runs where

- On each node (node-base, node-converged; not the audit image): the ctrl-exec
  `nagios-check` agent script from the pinned `ctrl-exec-plugins` input
  (release tag in `flake.nix`), allowlisted as the node script `nagios-check`
  under profile `node`. It reads no input; its arguments are check names.
  `nix/modules/hps-monitor.nix` installs it, a directory of plugins
  (`check_disk`, `check_load`, `check_procs` from
  monitoring-plugins, `check_mem` from the plugin repository, and HPS's own
  `check_zpool`, `check_fs`, `check_swap_use`, `check_osvc_hb` and usage checks
  `check_cpu`, `check_net`, `check_diskio`, `check_zpool_io` and `check_vms`) and
  `/etc/nagios-checks/checks.conf`.
- On the IPS: `bin/hps-monitor`, supervisor program `hps-monitor` running
  `hps-monitor loop`. It calls `scripts/hps-run.sh --json <fqdn> nagios-check --all`
  for each paired node and logs the result.

The targets are the paired nodes only: hosts of the registry that the dispatcher
also lists as agents (names starting `stale-` are ignored). No node script runs
on the IPS; a run of every node also checks the IPS's own resources and log
filesystems locally (see below). The host the IPS runs on is never checked.

## Who decides what

| Decided | By | Where |
| --- | --- | --- |
| Which checks run | the IPS, as `--all` (every check the node offers) | `bin/hps-monitor` |
| When | the IPS | cluster key `monitor_interval_seconds` |
| What a check name means: plugin, thresholds, timeout | the node | `/etc/nagios-checks/checks.conf`, generated by `hps-monitor.nix` |

The IPS sends the script name and `--all` and nothing else.

## The node's checks

| Name | Plugin and arguments | Where |
| --- | --- | --- |
| `disk_root` | `check_disk -w 20% -c 10% -p /` | every node |
| `load` | `check_load -r -w 1.5,1.2,1 -c 3,2.5,2` | every node |
| `mem` | `check_mem -w 10 -c 5` | every node |
| `procs` | `check_procs -k -w 1000 -c 2000` (user-space processes; kernel threads left out) | every node |
| `swap` | `check_swap_use -w 50 -c 80` (swap space and traffic, see below) | every node |
| `osvc_hb` | `check_osvc_hb` (the OpenSVC heartbeat, see below) | nodes that run om3 (converged, container hosts) |
| `zpool` | `check_zpool` (pool health; DEGRADED is WARNING, FAULTED and worse CRITICAL; capacity as perfdata) | storage nodes |
| `zpool_io` | `check_zpool_io` (pool I/O and capacity in bytes, see below) | storage nodes |
| `zpool_cap` | `check_zpool -m cap -w 80 -c 90` (how full each pool is, see below) | storage nodes |
| `disk_var_lib_containers`, `disk_var_lib_hps_ips` | `check_fs -p <mount> -w 80 -c 90` (the CNH state disk, see below) | container hosts |
| `disk_var_lib_hps_builder` | `check_fs -p /var/lib/hps-builder -w 80 -c 90` (the builder disk) | builders |
| `disk_other` | `check_fs -a -x <the role mounts> -w 80 -c 90` (every other persistent filesystem) | every node |
| `cpu` | `check_cpu` (CPU time by state, see below) | every node |
| `net` | `check_net` (traffic per interface, see below) | every node |
| `diskio` | `check_diskio` (throughput per whole disk, see below) | every node |
| `vms` | `check_vms` (CPU, memory, disk and network per running guest, and the paused guests, see below) | compute nodes |

A netbooted node runs from RAM: `/` is a tmpfs and the store is a squashfs.
`disk_root` therefore measures RAM taken by files written to `/`, and `mem` the
RAM left. The persistent filesystems and pools are the `disk_*` checks and
`zpool_cap` (below). Other thresholds are the plugin's example values.

## Persistent filesystems and pools

A full persistent disk stops what lives on it (lab 2026-11-12: cnh-001's
state disk filled, "No space left on device", and no check covered it). These
checks grade space and inode use, WARNING at 80% used or more and CRITICAL at
90%, the higher of the two counting:

- `disk_<mount slug>` (`check_fs -p`): one per role disk the image mounts,
  the slug being the mount point with `/` and `-` as `_`. Not mounted (no
  disk prepared yet) or on tmpfs is OK and says so: the data is then on the
  RAM root, which `disk_root` watches.
- `disk_other` (`check_fs -a`): every other mounted filesystem except RAM and
  pseudo filesystems (tmpfs, overlay, squashfs, proc, sysfs, cgroup, ...),
  network filesystems, ZFS (its datasets share the pool: `zpool_cap`), the
  role mounts above and a second mount of the same device (a bind mount).
  No such filesystem is OK. A check per mount point is not possible for
  these: `checks.conf` is fixed in the image and they are only known at run
  time, so their figures carry the slug as a prefix (`srv_used_pct`).
- `zpool_cap` (`check_zpool -m cap`): capacity of each imported pool from
  `zpool list`, health aside (that is `zpool`).

| Check | Status line and perf labels |
| --- | --- |
| `disk_<slug>` | `DISK OK - /var/lib/containers 41% used (12.3 GiB of 30.0 GiB), inodes 3%`; `used_pct`, `inode_pct` (left out where the filesystem has no fixed inode count), `used`, `size` (B) |
| `disk_other` | `DISK OK - 2 filesystems: /srv 41% (inodes 3%); /data 12% (inodes 1%)`; the same labels prefixed `<slug>_` |
| `zpool_cap` | `ZPOOL_CAP OK - 2 pools: lab 41% fast 3%`; `<pool>_cap` |

The thresholds are cluster keys, `monitor_disk_warn_pct` (default 80) and
`monitor_disk_crit_pct` (default 90). The node grades at 80 and 90 (they are
in its image); hps-monitor grades the same figures (`used_pct`, `inode_pct`,
`<pool>_cap`) again with the keys, so a change takes effect at the next tick
with no new image. A state the IPS changed says so in the line: `(graded at
warn 70% crit 85%)`. A warn not below crit, or a value outside 1 to 100, is
logged once and both defaults are used. `hps-ips-check` grades its `disk
resources` and `disk log` checks with the same keys.

The IPS's own filesystems: a run of every node (the loop's, or `hps-monitor
run` with no `--host`) also measures the filesystems of `$HPS_RESOURCES` and
`$HPS_LOG` with `df` and logs them as host `ips.<cluster domain>`, checks
`disk_resources` and `disk_log`, in the same form as a node's:

```
hps-monitor: host=ips.lab.hps check=disk_log state=CRITICAL DISK CRITICAL - /srv/hps-log 97% used (95.0 GiB of 97.9 GiB), inodes 34% on /srv | used_pct=97% inode_pct=34% used=...B size=...B
hps-monitor: host=ips.lab.hps checks=2 worst=CRITICAL duration=0.0
```

The node checks take effect with a new node image; the IPS's with the IPS's
tree.

## Usage checks: trend and baseline data

`cpu`, `net`, `diskio`, `zpool_io` and `vms` exist to collect numbers, not to
raise alarms (owner, 2026-11-11: data for trends as the lab scales out, and a
baseline for when it is put under pressure). Each is OK whenever it can read its
source, and says UNKNOWN only when it cannot (a missing `/proc/stat`, `zpool` or
`virsh` failing). The one exception is optional: `check_cpu -w BUSY -c BUSY`
applies thresholds to the busy percentage; `checks.conf` sets none.

`cpu`, `net`, `diskio` and `zpool_io` take two samples of a counter one
interval apart (`-i SECONDS`, 1 to 5, default 1) and report the difference as a
rate, so a value is the average over that one second, not over the tick; the
log line is a snapshot. `check_zpool_io` asks `zpool iostat -Hp 1 2` and uses
its second sample. `vms` samples once per run and rates against the sample the
previous run saved, so its rates are averages over the monitor interval
(below).

Perf labels are lower-case `[a-z0-9_-]` (dots and other characters in interface,
pool and guest names become `_`; the pool, disk, interface or guest name comes
first). The suffix says what the number is:

| Suffix or unit | Meaning |
| --- | --- |
| `_Bps` | bytes per second (plain number) |
| `_pps` | packets per second |
| `_iops` | operations per second |
| `%` | percent of the interval (or of a vCPU, see `vms`) |
| `B` | bytes, a level (`_alloc`, `_free`, `_rss`, `_mem`) |
| `c` | a counter's increase over the interval (errors, drops) |

| Check | Status line and perf labels |
| --- | --- |
| `cpu` | `CPU OK - 3.2% busy (iowait 0.1%, steal 0.0%)`; `busy` (100 - idle - iowait), `user`, `nice`, `system`, `iowait`, `irq`, `softirq`, `steal`, `idle` as % of the interval; `cpus` |
| `net` | `NET OK - rx 1.2 Mbit/s tx 0.4 Mbit/s (3 interfaces)`; per interface `<if>_rx_Bps`, `_tx_Bps`, `_rx_pps`, `_tx_pps` and `_rx_errors`, `_tx_errors`, `_rx_dropped`, `_tx_dropped` (counter deltas, `c`). Left out: `lo`, `veth*`, `vnet*` (guest taps; see `vms`) and interfaces that are down |
| `diskio` | `DISKIO OK - read 1.2 MB/s write 3.4 MB/s (2 disks)`; `disks`, and per whole disk (`sd*`, `vd*`, `xvd*`, `nvme<N>n<M>`; no partitions, `dm-*`, `md*`, `zd*`, `loop*`, `ram*`) `<dev>_rd_Bps`, `_wr_Bps` (sectors x 512), `_rd_iops`, `_wr_iops`, `<dev>_busy` (% of the interval with I/O in flight). A RAM node has no disk: `DISKIO OK - no disks | disks=0` |
| `zpool_io` | `ZPOOL_IO OK - read 2.0 MB/s write 3.5 MB/s (2 pools)`; `pools`, per pool `<pool>_alloc`, `_free` (B), `_rd_iops`, `_wr_iops`, `_rd_Bps`, `_wr_Bps`. No pool: `ZPOOL_IO OK - no pools` |
| `vms` | `VMS OK - 2 running VMs (rss 1.5 GiB)`; `vms`, per running guest `<vm>_cpu_pct` (guest CPU time / the time since the previous run; 100% is one full vCPU, so it can exceed 100), `_vcpus`, `_rss` (host memory the guest process holds), `_mem` (memory given to the guest), `_rd_Bps`, `_wr_Bps` (summed over its disks), `_rx_Bps`, `_tx_Bps` (summed over its NICs). Also `paused=<n>` (every run, 0 included) and per paused guest `<vm>_paused_<reason>=1`; a guest paused by a disk I/O error makes the check `VMS WARNING - 1 running VMs (rss 1.5 GiB), 1 paused: web (ioerror)` (exit 1). No guest: `VMS OK - no running VMs | vms=0 paused=0` |

`vms` asks `virsh domstats --list-running --list-paused --nowait --state` once per run: libvirtd does not wait for a
guest's state-change lock, which an earlier `domstats` it is still answering
can hold on a slow (nested) host, and leaves out the values that need it. A
label whose value a sample lacks is left out for that guest that time. The one
call gets 8 s of `nagios-check`'s 10 s; a slower call is
`VMS UNKNOWN - virsh domstats timed out after 8s`. The sample (time and one line
per guest) is saved in `/run/hps/check_vms.prev`, written atomically, and the
next run takes the rates from it. The first run, a saved sample older than 15
minutes (a reboot or a monitor pause) or one with no running guest in it gives
the counts and levels only and says so: `(rss 1.5 GiB, rates: no previous
sample)`, `previous sample too old`, `no guest in the previous sample`. A guest
started since the previous run gets its levels only; a counter that went
backwards (the guest was restarted under the same name) counts as 0. Before
(IPS-34 item 6) two calls of (9 - interval) / 2 s each timed out on every
nested TCH while guests were being created on the same host.

Time budget: `nagios-check` runs the checks one after another within its 50 s
budget, 10 s at most each. The four two-sample checks add about 4 s to a node's
run (the `cpu`, `net`, `diskio` and `zpool_io` waits do not overlap) and `vms`
what its one `virsh` call takes (8 s at most), well inside the budget at the
lab's 30 s interval, but a shorter `monitor_interval_seconds` or more samplers
would not be. Each plugin finds its tools itself: the build
puts coreutils and awk on its `PATH` and, for `zpool_io` and `vms`, the
absolute store path of `zpool` and `virsh` (libvirt is on compute nodes with the
compute profile).

### Paused guests

libvirt pauses a guest whose disk I/O fails when its disks carry
`error_policy stop` (`vm_disk_error_policy`, the default; `docs/STORAGE-FAULTS.md`).
Such a guest is not running, so it is not in `vms`, `<vm>_cpu_pct` or the saved
sample, and before this nothing showed it. `check_vms` now reads each guest's
state and pause reason from the same `domstats` call (no second call, so the
8 s budget is shared) and reports:

- `paused=<n>`, on every run of this version, 0 included. A node on an older
  image prints no such figure; the IPS reads a missing `paused` as "cannot tell",
  never as "none paused", so nothing opens or resolves because it is absent.
- `<vm>_paused_<reason>=1` per paused guest, with `<reason>` one of `ioerror`,
  `user`, `migrating`, `saving`, `dumping`, `watchdog`, `fromsnapshot`,
  `shuttingdown`, `creatingsnapshot`, `crashed`, `startingup`, `postcopy`,
  `postcopyfailed`, `unknown`, or `code<N>`.
- WARNING (exit 1) when a guest is paused for `ioerror`: it is an outage. A guest
  paused for any other reason (an operator's `virsh suspend`) is named in the text
  and the check stays OK.

The IPS opens a `guest-paused` issue per `ioerror` guest from that line and the
healer resumes it once its disks are healthy (`docs/ISSUES.md`, "A paused
guest"). A guest that is resumed leaves `paused` at the next run.

### swap and osvc_hb

- `swap` (`check_swap_use`): `SwapTotal` and `SwapFree` of `/proc/meminfo`, and
  `pswpin` and `pswpout` of `/proc/vmstat` sampled twice one second apart.
  A RAM-booted node usually has no swap: `SWAP OK - no swap configured`,
  `swap_total=0` (never WARNING or UNKNOWN for that). WARNING at 50% used or
  when pages were swapped in during the sample (memory pressure), CRITICAL at
  80% used; graded on the node (the IPS does not grade it again: the cluster
  keys `monitor_disk_*_pct` are for filesystems and pools). Perfdata:
  `used_pct`, `swap_total`, `swap_used`, `swap_free` (B), `swap_in_Bps`,
  `swap_out_Bps` (bytes per second: pages x the page size). Example: `SWAP OK -
  3.1% used (32.0 MiB of 1.0 GiB), in 0.0 KiB/s out 0.0 KiB/s`. A node may have
  swap (the lab DL360 has 4 GiB) or not.
- `osvc_hb` (`check_osvc_hb`): `om daemon status --format json`, read as the
  `osvc-status` node script reads it (`hps-osvc status`): a peer is beating when
  any heartbeat stream sees it beating, stale otherwise. OK when every peer
  beats (or there is none); WARNING when a peer is stale; CRITICAL when the
  beating nodes (beating peers and this node) are fewer than a quorum of
  (peers + 1) / 2 + 1; UNKNOWN when `om` is not installed or the daemon does not
  answer (8 s). The peers are the nodes of the node list the IPS gave om3, which
  holds only hosts that were delivered an om3 configuration (docs/OPENSVC.md), so
  a paired host never delivered to is not a stale peer. Perfdata `peers`, `beating`, `stale`. Example: `OSVC_HB WARNING
  - 3 of 4 peers beating; stale: tch-004`. The issue register opens `om3-hb`
  issues from om3's own send error lines (docs/ISSUES.md).

## Log lines

Every line goes to syslog (tag `hps`, facility `local0`; OK is `info`, WARNING
`warning`, CRITICAL and UNKNOWN `err`) and, for `hps-monitor run`, to stdout. OK
results are logged too. rsyslog files the check, summary and tick lines in
`metrics.log` (the file `hps-metrics` reads, rotated daily; `docs/LOGGING.md`)
and in the day file `ips/hps/<date>.log` (the `from=ips` rules of
`hps-issue-watch` read that one).

The lines that matter to an operator are also **event lines**, written to
`events.log` and read by `hps-log events` and `hps-log attention`
(`docs/LOGGING.md`): the host-state lines below start with the marker
`HPS-ALERT pri=<priority> kind=monitor subject=<fqdn> state=<state>` (UNREACHABLE
is a `warning`, PAIR_FAILED `urgent`, REACHABLE a `notice`, STOPPED `info`) and
keep their text after it. A check that is not OK also gets one event line when
its state changes (`subject=<fqdn>/<check>`, `warning` for WARNING and UNKNOWN,
`urgent` for CRITICAL) and again every 50 minutes while it holds; OK after a bad
state is a `notice`. The monitor also logs `started`, `stopped` and a
`service` heartbeat every 50 minutes (even with the interval 0), so a quiet
cluster still has event lines in the last hour.

```
hps-monitor: host=sch-001.hps.test check=mem state=OK MEM OK - 62% available (9.8 GiB of 15.6 GiB) | available=10522MB available_pct=62%
hps-monitor: host=sch-001.hps.test checks=6 worst=OK duration=1.4
hps-monitor: host=tch-002.hps.test state=UNREACHABLE hps-run exit 4: hps-run: no registered agent for tch-002.hps.test
hps-monitor: tick hosts=3 duration=1.9
```

- `host=<fqdn> check=<name> state=<state> <summary> | <label=value[unit] ...>`:
  one per check; the performance data is omitted when the plugin gave none.
- `host=<fqdn> checks=<n> worst=<state> duration=<s>`: one per host.
- `host=<fqdn> state=UNREACHABLE <reason>`: the node could not be asked (not
  registered, call failed or timed out after 70 s, unreadable reply).
- `host=<fqdn> state=PAIR_FAILED since=<UTC time> reboots=<n> ...` (`err`):
  the IPS gave up pairing the host (registry `pair_failed_at`, ADR 0002
  amendment 2026-11-12). It is not paired, so it is not checked; the loop logs
  the line when it first sees it and then every 10 minutes.
- `host=<fqdn> state=STOPPED workload=<name> vm=<vm> recorded state
  <stopped|suspended>; not checked` (`info`): the node is a VM of a workload
  (the builder), and the workload's record (cluster key `workload_<name>`)
  says that VM is `stopped` or `suspended`: `hps-workload stop` or `suspend`
  did it on purpose. Such a node is not called (a call to a node that is off
  makes ctrl-exec log an error each time) and is not UNREACHABLE; the loop
  logs the line when it first sees it and then every 10 minutes. The VM is
  matched by the MACs in its record (`vms.<vm>.macs`) against the registry
  hosts. Only a recorded `stopped` or `suspended` counts: with any other
  state, no record, an unreadable record or no MACs the node is checked as
  before, and after `hps-workload start` or `resume` it is a target again at
  the next tick. `hps-monitor run --host <host>` calls a node it is given by
  name whatever its record says.
- `tick hosts=<n> duration=<s>`: one per run (the hosts called), so the cadence is visible.
- `tick skipped missed=<k> run=<s>s interval=<n>s`: a run took longer than the
  interval; the ticks it covered are skipped (runs never overlap).
- `disabled (monitor_interval_seconds=0)` and `enabled interval=<n>s`.

Nodes are called in parallel, eight at a time.

## Reading the results: hps-metrics

`hps-metrics` reads hps-monitor's lines back from the IPS's own log tree, per
host. It is read-only and an ips-admin tool, so an operator runs it through
`hps-op` (`docs/OPERATOR.md`); the cluster browser's utilisation tiles and the
health badge's monitor row call it.

    hps-metrics last <mac|hostname|ips|all> [--json]
    hps-metrics series <mac|hostname|ips|all> [--hours N] [--step S] [--json]
    hps-metrics series <mac|hostname> --guest <vm> [--hours N] [--step S] [--json]

- `last`: each host's newest result: the checks of its newest run (the lines
  before its newest `checks=<n> worst=<state>` line) with state, text and
  perfdata values, its utilisation and compound, and `unreachable` when a newer
  `UNREACHABLE` or `PAIR_FAILED` line says it was not answered, or `stopped`
  and `stopped_at` (worst `STOPPED`) when a newer `STOPPED` line says it is a
  VM of a stopped workload. Hosts with no
  line in the newest 15 minutes (or 3 intervals, when longer) are left out.
- `series`: the host's utilisation per bucket of `--step` seconds (30 to 86400,
  default 300) over the last `--hours` (1 to 168, default 24), at most 10080
  buckets: the max of each utilisation and raw value within a bucket, the last
  state of each check, and `_host` (the host's worst, `UNREACHABLE` or
  `STOPPED`).
  Empty buckets are `null`. `series all` gives every host's compound only, for
  an overview in one call.
- `ips` is the IPS itself (`ips.<domain>`, its `disk_resources` and `disk_log`
  checks).
- `series <host> --guest <vm>`: one guest's series, see "Per guest" below.

### Per guest

A compute host's `vms` check reports each running guest's `<vm>_cpu_pct`,
`_rss`, `_mem`, `_vcpus`, `_rd_Bps`, `_wr_Bps`, `_rx_Bps` and `_tx_Bps`
("The node's checks"). `series` records them as raw values under the guest's
name, bucketed like the host's labels (the max within a bucket; empty buckets
`null`). A guest that disappears simply stops: its buckets after the last
sample are `null`.

- `series <host> --json` lists the guests that have samples in the window as
  `guests: [name, ...]` (names only; the values are not in this answer, so it
  stays the size it was).
- `series <host> --guest <vm> [--json]` answers for that guest:
  `{target, host, name, mac, source, hours, step, start, t, guest, raw, units,
  guests, lines, truncated}` where `raw` maps each label present
  (`cpu_pct`, `rss`, `mem`, `vcpus`, `rd_Bps`, `wr_Bps`, `rx_Bps`, `tx_Bps`) to
  an array of one value or `null` per bucket in `t`, and `units` gives `%` for
  `cpu_pct`, `B` for `rss` and `mem`, `B/s` for the `_Bps` labels and an empty
  string for `vcpus`. `cpu_pct` is of one vCPU (100 = one full vCPU, it can
  exceed 100). A guest with no sample in the window exits 4 (`notfound`);
  `--guest` with `all` or `ips`, or on `last`, is usage (2).
- **Cap:** at most 64 guests per host (`HPS::Metrics::MAX_GUESTS`): in each
  `vms` line the first 64 names in sorted order are read, so a guest past the
  64th has no series and is not listed. Retention is `log_metrics_retention_days` (default 30); a
  call reads at most 512 MiB as above and at most 168 hours.

Utilisation, in percent:

| Resource | From |
| --- | --- |
| cpu | `busy` (check `cpu`) |
| mem | 100 - `available_pct` (check `mem`) |
| load | `scaled_load1` (load per core) x 100, capped at 100 (check `load`) |
| disk | the worst `*used_pct` or `*inode_pct` of the `disk_*` checks; `disk_root` (plain `check_disk`) gives free space and free inodes in its text: 100 - the lower |
| pool | the worst `<pool>_cap` (check `zpool` or `zpool_cap`) |
| diskio | the busiest device's `<dev>_busy`: shown, not in the compound (time with a request in flight, not a share of capacity) |
| swap | `used_pct` (check `swap`; 0 on a node with no swap): shown, not in the compound (swap in use is not pressure by itself; the check's state carries the swap-in rate). Raw: `swap_total_bytes`, `swap_in_Bps`, `swap_out_Bps` (bytes, bytes per second) |
| net | none: no link capacity is recorded (the audit's speed is null); the busiest interface's rx and tx bytes per second are given as raw series |

The **compound** is the max of cpu, mem, load, disk and pool: anything high
makes it high. Levels: ok below 70, warning below 90, critical from 90. The text
output marks a resource outside the compound with `*` (`diskio*`, `swap*`); the
JSON of both `last` and `series` lists the resources that are in it
(`in_compound`).

Source: `<log>/metrics.log` and its rotated files `metrics-<date>.log[.gz]` when
there are any (rsyslog on the IPS writes it, `docs/LOGGING.md`; retention
`log_metrics_retention_days`, default 30), else `<log>/ips/hps/<date>.log`, which
every IPS writes (hps-monitor logs with tag `hps`); `source` names the one read. A collector's
`metrics.log` also holds the lines forwarded from its inner IPSs: only hosts in
this cluster's DNS domain are read, so each IPS answers for its own hosts (an
inner IPS answers from its own disk). Files are read from the end; a call reads
at most 512 MiB (`truncated` says when it stopped there).

## The interval

Cluster key `monitor_interval_seconds`: `0` disables, otherwise 10 to 86400
seconds; default 60 (a value outside the range is logged and 60 used). It is read
before every tick, so a change applies at the next one; while disabled the loop
rechecks the key every 60 seconds. `hps-cluster-config set monitor_interval_seconds 30`.
