# Guest confinement on the compute role

Brief requirement: enable the strongest guest confinement libvirt supports on
NixOS 26.05 and document what it is. This file states what
`nix/modules/profiles/compute.nix` configures, what each item protects against,
what is **not** enabled, and how to check each item on a running node
(`$NODE`, guest `$VM`).

Status: written against the nixpkgs 26.05 sources (`libvirtd.nix`, the libvirt
and QEMU package expressions) and evaluated by `nix flake check` in the builder
container (the AppArmor profiles are parsed there). Nothing has been booted:
every "configured" below is a claim to be confirmed with the checks in the last
section; the lab runsheet step 1 ("confinement reported") does that.

## The threat

A guest that escapes QEMU lands in the QEMU process on the node. The node holds
other guests' disks, the pool keys delivered by the IPS and the ctrl-exec
credentials. Confinement limits what that process can do, in layers, so one
failing layer is not the end.

## What is configured

| Layer | Setting (file) | Protects against |
| --- | --- | --- |
| Unprivileged QEMU | `virtualisation.libvirtd.qemu.runAsRoot = false` renders `user`/`group = "qemu-libvirtd"` into qemu.conf | An escape being root: QEMU runs as `qemu-libvirtd`, not as root |
| No capabilities | `clear_emulator_capabilities = 1` | An escape using Linux capabilities (raw sockets, `CAP_SYS_ADMIN`, ...) |
| QEMU seccomp sandbox | `seccomp_sandbox = 1`; nixpkgs QEMU is built with seccomp (`seccompSupport`, not the `minimal` build). libvirt starts QEMU with `-sandbox on,obj-blacklist=on,elevateprivileges=deny,spawn=deny,resourcecontrol=deny` | An escape running programs or forking (`spawn=deny`), raising privileges (`elevateprivileges=deny`) or changing resource limits (`resourcecontrol=deny`) |
| Per-guest disk ownership | `dynamic_ownership = 1` (libvirt's DAC security driver): a guest's disks, including its `/dev/md*` mirror, are owned by `qemu-libvirtd` only while that guest runs and are restored afterwards | One guest's QEMU opening another guest's block devices |
| Device cgroup | libvirt default (not changed): the guest's cgroup allows only the devices of its definition | A QEMU process opening other host devices |
| No format probing | `allow_disk_format_probing = 0` | A guest writing a qcow2/backing-file header into a raw disk so the host later reads an arbitrary file |
| AppArmor (per-guest profile) | `security.apparmor.enable = true` (kernel `apparmor=1 security=apparmor`, userspace parser); `security_driver = "apparmor"` and `security_default_confined = 1` in qemu.conf; the libvirt profiles in `compute-apparmor.nix` (see "AppArmor layer") | A QEMU process reading or writing anything outside its generated profile: no write or execute in `/nix/store`, only its own disks, log, pid and monitor socket |

Mechanism summary: the layers are the unprivileged user, dropped capabilities,
the QEMU seccomp sandbox, per-guest DAC ownership, the device cgroup and, from
CS-3.4a, a per-guest AppArmor profile generated by `virt-aa-helper`. The
AppArmor layer is confirmed on a lab node (`lab/REPORT-2026-11-10.md`, pin
2c3e5b6): the security models are `apparmor, dac`, libvirtd runs confined and
the kernel logs no denials. The first boot ran libvirtd unconfined because
nixpkgs wraps the daemon; the profile attaches to the wrapped binary. Commit
9defece lets a guest exec the wrapped QEMU ELF under its profile. Before CS-3.4a the image reported security models `none, dac`
only, because nixpkgs libvirt ships no profiles (owner decision 4 of
`plans/phase-3.md` section 5: ship them).

## What is not enabled, and why

* **Mount namespaces** (`namespaces = []`, the NixOS module default). libvirt can
  give each QEMU a private `/dev`; NixOS ships it off and the mirrors here are
  assembled and re-added while guests run (`mirror-rejoin`), so device nodes
  appear after the guest started. Turn it on only after a lab test of that case.
* **`security_require_confined`** stays `0`. With `1` libvirt refuses to start any
  guest that is not AppArmor-confined. `security_driver = "apparmor"` already
  makes libvirtd refuse to start when the driver cannot load; set
  `security_require_confined = 1` once the lab step has shown guests running
  as `libvirt-<uuid> (enforce)`.
* **SELinux / sVirt**: not supported by NixOS.
* **Hugepages, KSM, memory ballooning policy**: resource settings, not confinement.

## AppArmor layer

Shipped by `nix/modules/profiles/compute-apparmor.nix` (imported by
`compute.nix`), through `security.apparmor`:

| What | Where |
| --- | --- |
| `libvirtd` profile (policy, enforce), named by the daemon binary `<libvirt>/sbin/.libvirtd-wrapped` (`sbin/libvirtd` is a bash wrapper that execs it; libvirt probes `/proc/self/exe`, which is the wrapped binary) | loaded by `apparmor.service` |
| `virt-aa-helper` profile (policy, enforce), named by `<libvirt>/libexec/virt-aa-helper` | loaded by `apparmor.service` |
| `abstractions/libvirt-qemu`: what any guest's QEMU may do | `/etc/apparmor.d/abstractions/libvirt-qemu` |
| `TEMPLATE.qemu`, upstream's, unchanged | `/var/lib/apparmor.d/libvirt/TEMPLATE.qemu` (tmpfiles link) |
| Per-guest profile `libvirt-<uuid>` and its disks file `libvirt-<uuid>.files`, written by `virt-aa-helper` when a guest starts | `/var/lib/apparmor.d/libvirt/` |

The profiles are upstream libvirt v12.2.0's with the Debian paths replaced by
store paths. The guest abstraction allows read and map (not write, not execute)
on `/nix/store/**` and execute only on the QEMU binary; it leaves out sound, USB,
spice, swtpm, passt, ceph, save/restore helpers and PPC lines, and keeps only
`setuid`, `setgid` and `ipc_lock` of upstream's capabilities (QEMU runs with
none). Each guest's disks are not in the abstraction: `virt-aa-helper` resolves
the disk path in the domain XML (`/dev/md/$NAME` becomes `/dev/mdN`) and writes
`"/dev/mdN" rwk,` into the guest's `.files`, with the guest's log, pid and
monitor socket.

Compile-time facts of the nixpkgs libvirt that this module works around:

* `APPARMOR_DIR` is `/var/lib/apparmor.d`, not `/etc/apparmor.d` (the latter is
  a read-only link farm on NixOS). The parser finds `libvirt/<uuid>.files`
  through an extra `Include` in `/etc/apparmor/parser.conf`, supplied by a
  package whose `etc/apparmor.d` points at `/var/lib/apparmor.d`.
* `virt-aa-helper` runs `/sbin/apparmor_parser` as an absolute path; NixOS has no
  `/sbin`, so tmpfiles creates the link to the store parser. The `libvirtd`
  profile denies the daemon both the link and the parser, so profiles are only
  loaded through `virt-aa-helper`.
* libvirt's driver probe needs the daemon itself confined and
  `TEMPLATE.qemu` present, hence `libvirtd.service` requires and is ordered
  after `apparmor.service`, and `security_driver = "apparmor"` makes a driver
  that cannot load a start failure of libvirtd instead of a quiet fall back
  to `dac`.

Build-time check: `checks.<system>.apparmor-profiles` (flake.nix) runs
`apparmor_parser -Q -K` over the evaluated `libvirtd` and `virt-aa-helper`
policies, the template (which includes the abstraction) and a sample generated
per-guest profile with a `.files` include. A syntax error fails
`nix flake check`. It proves the profiles parse; it does not prove the kernel
accepts them or that a guest can run under them.

Verify on the node (all read-only):

* `vm-confinement-report $VM` shows `model=apparmor` and a `libvirt-<uuid>`
  label in its last line, with a guest running.
* `cat /sys/kernel/security/apparmor/profiles` lists the daemon, the helper and
  `libvirt-<uuid> (enforce)` while a guest runs.
* `ls /var/lib/apparmor.d/libvirt/` holds `TEMPLATE.qemu` and, for a started
  guest, `libvirt-<uuid>` and `libvirt-<uuid>.files`.
* Failures: `node-journal libvirtd` (driver or helper errors, "template does not
  exist", "failed to run apparmor_parser") and `node-journal apparmor` (a
  policy the parser rejected at boot). Denials appear in the kernel log as
  `apparmor="DENIED"` lines; they name the profile and the path.

Not verified until the lab step: that the kernel loads the profiles, that
libvirt activates the driver, and that a guest on a zvol-backed md mirror
starts and runs under its profile.

## Verify on the node

Run these read-only commands on `$NODE` with a guest `$VM` running (`$PID` is
the guest's QEMU process id, from `ps` or `virsh dominfo`).

1. Which security drivers libvirt activated:

   ```
   virsh -c qemu:///system capabilities | grep -A3 secmodel
   virsh -c qemu:///system dominfo $VM | grep -i security
   ```

   Expect `apparmor` and `dac` in `capabilities`, and `Security model: apparmor`
   in `dominfo`. `dac` or `none` there means AppArmor is not active (the DAC
   layer still applies).

2. The QEMU process runs unprivileged and without capabilities:

   ```
   ps -o pid,user,label,args -C qemu-system-x86_64
   grep -E 'CapEff|CapPrm|NoNewPrivs|Seccomp' /proc/$PID/status
   ```

   Expect user `qemu-libvirtd`, `CapEff: 0000000000000000`, `Seccomp: 2`
   (a filter is installed). The sandbox is also on the command line:
   `grep -- '-sandbox' /var/log/libvirt/qemu/$VM.log` shows
   `-sandbox on,obj-blacklist=on,elevateprivileges=deny,spawn=deny,resourcecontrol=deny`.

3. The AppArmor label of the QEMU process:

   ```
   cat /proc/$PID/attr/current
   ps -o pid,label -p $PID
   ```

   `libvirt-<uuid> (enforce)` means confined; `unconfined` means not.

4. AppArmor loaded in the kernel and the profiles present:

   ```
   cat /sys/module/apparmor/parameters/enabled
   cat /sys/kernel/security/apparmor/profiles
   ```

   `Y`, a line `<libvirt store path>/sbin/.libvirtd-wrapped (enforce)`, one for
   `<libvirt store path>/libexec/virt-aa-helper (enforce)` and one
   `libvirt-<uuid> (enforce)` per running guest.

5. The settings reached libvirt: `grep -E 'seccomp|clear_emulator|dynamic_ownership|allow_disk_format|^user|^group' /var/lib/libvirt/qemu.conf`.

6. A guest's disk is owned by the unprivileged user only while it runs:
   `ls -l /dev/md/*` (or the `/dev/mdN` of the guest's mirror) during and after.

Record the results of 1 to 4 in the phase-3 report; `dac` or `unconfined` in 1
or 3 means the AppArmor layer failed on the node (see "AppArmor layer" for where
to look).

## Node script: vm-confinement-report

`vm-confinement-report [$VM]` (ctrl-exec allowlisted, profile `node`, read-only)
runs checks 1 to 5 above in one call and prints each as a labelled line:

| Label | Check | Source |
| --- | --- | --- |
| `CHECK1 libvirt secmodels` / `CHECK1 dominfo $VM` | 1 | `virsh capabilities`, `virsh dominfo $VM` ("Security model") |
| `CHECK2 $VM` | 2 | `/proc/$PID/status`: user (from `Uid`), `CapEff`, `CapPrm`, `NoNewPrivs`, `Seccomp` |
| `CHECK3 $VM` | 3 | `/proc/$PID/attr/current` |
| `CHECK4 apparmor kernel enabled`, `CHECK4 apparmor profiles` | 4 | `/sys/module/apparmor/parameters/enabled`, `/sys/kernel/security/apparmor/profiles` (counts of `libvirtd` and `libvirt-*` profiles) |
| `CHECK5 qemu.conf` | 5 | the seccomp, capability, ownership, disk-format, `security_*`, `user` and `group` lines of `/var/lib/libvirt/qemu.conf` |

The guest's QEMU process is the one whose command line holds `guest=$VM,`. With
no `$VM` every running guest is examined. A guest that is not running is a
result (`no guest running`), never a failure: the script exits 0 (2 only for a
usage error).

The last line is the one the IPS parses:

```
CONFINEMENT model=<apparmor|dac|none> qemu_user=<user|-> seccomp=<0|1|2|-> apparmor_kernel=<Y|N|-> label=<label|->
```

`model` is the guest's `dominfo` "Security model" (with no guest running, the
first model `virsh capabilities` lists, else `none`). `label` is the AppArmor
profile name without the ` (enforce)` suffix, `unconfined` when the process is
not confined. A `-` means "not observed". Reading the line: `model=dac` or
`label=unconfined` means the AppArmor layer is not in effect (see "AppArmor
layer"); `model=apparmor` with a `libvirt-<uuid>` label is confinement in effect.
The script was tested against shimmed `virsh` and a fake `/proc` and `/sys`
only; its output on a real node is unverified until the lab runsheet step 1.
