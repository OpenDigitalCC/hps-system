# Guest confinement on the compute role

Brief requirement: enable the strongest guest confinement libvirt supports on
NixOS 26.05 and document what it is. This file states what
`nix/modules/profiles/compute.nix` configures, what each item protects against,
what is **not** enabled, and how to check each item on a running node
(`$NODE`, guest `$VM`).

Status: written against the nixpkgs 26.05 sources (`libvirtd.nix`, the libvirt
and QEMU package expressions). Nothing here has been evaluated or run: `nix` is
not installed on the development host. Every "configured" below is a claim to
be confirmed with the checks in the last section; the lab runsheet step 1
("confinement reported") does that.

## The threat

A guest that escapes QEMU lands in the QEMU process on the node. The node holds
other guests' disks, the pool keys delivered by the IPS and the ctrl-exec
credentials. Confinement limits what that process can do, in layers, so one
failing layer is not the end.

## What is configured

| Layer | Setting (file) | Protects against |
| --- | --- | --- |
| Unprivileged QEMU | `virtualisation.libvirtd.qemu.runAsRoot = false` renders `user`/`group = "qemu-libvirtd"` into qemu.conf | An escape being root: QEMU runs as `qemu-libvirtd`, not as root |
| No capabilities | `clear_emulator_capabilities = 1` | An escape using Linux capabilities (raw sockets, `CAP_SYS_ADMIN`, ...) |
| QEMU seccomp sandbox | `seccomp_sandbox = 1`; nixpkgs QEMU is built with seccomp (`seccompSupport`, not the `minimal` build). libvirt starts QEMU with `-sandbox on,obj-blacklist=on,elevateprivileges=deny,spawn=deny,resourcecontrol=deny` | An escape running programs or forking (`spawn=deny`), raising privileges (`elevateprivileges=deny`) or changing resource limits (`resourcecontrol=deny`) |
| Per-guest disk ownership | `dynamic_ownership = 1` (libvirt's DAC security driver): a guest's disks, including its `/dev/md*` mirror, are owned by `qemu-libvirtd` only while that guest runs and are restored afterwards | One guest's QEMU opening another guest's block devices |
| Device cgroup | libvirt default (not changed): the guest's cgroup allows only the devices of its definition | A QEMU process opening other host devices |
| No format probing | `allow_disk_format_probing = 0` | A guest writing a qcow2/backing-file header into a raw disk so the host later reads an arbitrary file |
| MAC confinement attempt | `security.apparmor.enable = true` (kernel `apparmor=1 security=apparmor` and the userspace parser); `security_default_confined = 1`; no explicit `security_driver`, so libvirt probes | A QEMU process reading or writing anything outside its generated profile |

Mechanism summary: the layers that are certain to be in effect are the
unprivileged user, dropped capabilities, the QEMU seccomp sandbox, per-guest
DAC ownership and the device cgroup. AppArmor is the strongest libvirt
mechanism (it adds a per-guest profile generated by `virt-aa-helper`), but it is
**not confirmed** on NixOS 26.05:

* libvirt in nixpkgs is built with the AppArmor security driver
  (`secdriver_apparmor`), and the image loads AppArmor;
* the libvirt package installs its profile templates (`TEMPLATE.qemu`, the
  `libvirtd` profile) below `/var/lib/apparmor.d` in its own output
  (`--sysconfdir=/var/lib`), and the NixOS libvirtd module does not copy or
  load them. libvirt's start-up probe is expected to find no usable AppArmor
  driver and continue with the DAC driver only, without an error (this is the
  reading of the sources, not an observation);
* so the image may run with `Security model: dac`. If the checks below show
  that, AppArmor is not providing confinement, and the fix is a decision for the
  owner (plan decision 4): ship the libvirt profiles through
  `security.apparmor.policies` (a reviewed change, not a guess made blind).

## What is not enabled, and why

* **Mount namespaces** (`namespaces = []`, the NixOS module default). libvirt can
  give each QEMU a private `/dev`; NixOS ships it off and the mirrors here are
  assembled and re-added while guests run (`mirror-rejoin`), so device nodes
  appear after the guest started. Turn it on only after a lab test of that case.
* **`security_require_confined`** stays `0`. With `1` libvirt refuses to start any
  guest when no MAC driver is active, which on this image is exactly the
  unconfirmed case. Set it to `1` once AppArmor is confirmed.
* **SELinux / sVirt**: not supported by NixOS.
* **Hugepages, KSM, memory ballooning policy**: resource settings, not confinement.

## Verify on the node

Run these read-only commands on `$NODE` with a guest `$VM` running (`$PID` is
the guest's QEMU process id, from `ps` or `virsh dominfo`).

1. Which security drivers libvirt activated:

   ```
   virsh -c qemu:///system capabilities | grep -A3 secmodel
   virsh -c qemu:///system dominfo $VM | grep -i security
   ```

   `Security model: apparmor` means AppArmor is active;
   `dac` or `none` means it is not (the DAC layer still applies).

2. The QEMU process runs unprivileged and without capabilities:

   ```
   ps -o pid,user,label,args -C qemu-system-x86_64
   grep -E 'CapEff|CapPrm|NoNewPrivs|Seccomp' /proc/$PID/status
   ```

   Expect user `qemu-libvirtd`, `CapEff: 0000000000000000`, `Seccomp: 2`
   (a filter is installed). The sandbox is also on the command line:
   `grep -- '-sandbox' /var/log/libvirt/qemu/$VM.log` shows
   `-sandbox on,obj-blacklist=on,elevateprivileges=deny,spawn=deny,resourcecontrol=deny`.

3. The AppArmor label of the QEMU process:

   ```
   cat /proc/$PID/attr/current
   ps -o pid,label -p $PID
   ```

   `libvirt-<uuid> (enforce)` means confined; `unconfined` means not.

4. AppArmor loaded in the kernel and the profiles present:

   ```
   cat /sys/module/apparmor/parameters/enabled
   cat /sys/kernel/security/apparmor/profiles
   ```

   `Y`, and a profile line for `libvirtd` plus one `libvirt-<uuid>` per running
   guest, when libvirt's AppArmor driver is in use.

5. The settings reached libvirt: `grep -E 'seccomp|clear_emulator|dynamic_ownership|allow_disk_format|^user|^group' /var/lib/libvirt/qemu.conf`.

6. A guest's disk is owned by the unprivileged user only while it runs:
   `ls -l /dev/md/*` (or the `/dev/mdN` of the guest's mirror) during and after.

Record the results of 1 to 4 in the phase-3 report; a result of `dac` or
`unconfined` in 1 or 3 is the finding that decision 4 in `plans/phase-3.md` §5
needs.

## Node script: vm-confinement-report

`vm-confinement-report [$VM]` (ctrl-exec allowlisted, profile `node`, read-only)
runs checks 1 to 5 above in one call and prints each as a labelled line:

| Label | Check | Source |
| --- | --- | --- |
| `CHECK1 libvirt secmodels` / `CHECK1 dominfo $VM` | 1 | `virsh capabilities`, `virsh dominfo $VM` ("Security model") |
| `CHECK2 $VM` | 2 | `/proc/$PID/status`: user (from `Uid`), `CapEff`, `CapPrm`, `NoNewPrivs`, `Seccomp` |
| `CHECK3 $VM` | 3 | `/proc/$PID/attr/current` |
| `CHECK4 apparmor kernel enabled`, `CHECK4 apparmor profiles` | 4 | `/sys/module/apparmor/parameters/enabled`, `/sys/kernel/security/apparmor/profiles` (counts of `libvirtd` and `libvirt-*` profiles) |
| `CHECK5 qemu.conf` | 5 | the seccomp, capability, ownership, disk-format, `security_*`, `user` and `group` lines of `/var/lib/libvirt/qemu.conf` |

The guest's QEMU process is the one whose command line holds `guest=$VM,`. With
no `$VM` every running guest is examined. A guest that is not running is a
result (`no guest running`), never a failure: the script exits 0 (2 only for a
usage error).

The last line is the one the IPS parses:

```
CONFINEMENT model=<apparmor|dac|none> qemu_user=<user|-> seccomp=<0|1|2|-> apparmor_kernel=<Y|N|-> label=<label|->
```

`model` is the guest's `dominfo` "Security model" (with no guest running, the
first model `virsh capabilities` lists, else `none`). `label` is the AppArmor
profile name without the ` (enforce)` suffix, `unconfined` when the process is
not confined. A `-` means "not observed". Reading the line: `model=dac` or
`label=unconfined` is the finding that decision 4 in `plans/phase-3.md` §5
needs; `model=apparmor` with a `libvirt-<uuid>` label is confinement in effect.
The script was tested against shimmed `virsh` and a fake `/proc` and `/sys`
only; its output on a real node is unverified until the lab runsheet step 1.
